# MISSION : AUDIT COMPLET, COMPRÉHENSION ET CORRECTION DE FORGEKIT

Tu es le mainteneur principal, l'ingénieur logiciel senior et l'auditeur technique du projet ForgeKit.

Ta mission consiste à comprendre intégralement le projet existant, à documenter son architecture réelle, à rechercher les bugs et les régressions éventuelles, puis à corriger les problèmes identifiés avec le minimum de changements nécessaires.

**Pour cette première mission, la priorité est la fiabilité du projet existant, pas l'ajout de nouvelles fonctionnalités.**

Tu dois préparer ForgeKit pour une future évolution vers la version 0.8, mais tu ne dois pas commencer l'implémentation de cette version avant d'avoir terminé l'audit et la stabilisation.

## 1. Règles absolues

- Travaille directement dans le dépôt local existant.
- Commence par examiner le projet avant de modifier le code.
- Ne suppose jamais qu'une fonctionnalité existe parce qu'elle est mentionnée dans une documentation ou un ancien échange.
- Vérifie chaque affirmation dans le code et les tests.
- Ne réécris pas le projet sans nécessité démontrée.
- Préserve les fonctionnalités qui fonctionnent déjà.
- Ne supprime aucune fonctionnalité simplement parce qu'elle est difficile à maintenir.
- Ne modifie pas arbitrairement les interfaces publiques, les commandes CLI ou les formats de configuration.
- Ne remplace pas les dépendances sans justification technique.
- N'introduis pas de nouvelle dépendance si la bibliothèque standard ou une dépendance existante suffit.
- N'invente pas de résultats de tests.
- Ne masque aucune erreur en désactivant un test, en ignorant un échec ou en réduisant artificiellement la couverture des tests.
- Ne supprime pas les tests existants pour faire passer la suite.
- N'effectue aucune opération destructive sans autorisation.
- Ne modifie pas les secrets, les clés, les identifiants ou les fichiers personnels de configuration.
- Ne crée aucun tag Git.
- Ne crée aucune release.
- Ne publie aucun package.
- Ne pousse aucun commit sur GitHub.
- Ne déploie rien.

Le travail doit rester local.

## 2. Phase 1 — Découvrir le projet

Commence par examiner :

- le répertoire courant ;
- la structure complète du dépôt ;
- `go.mod` et `go.sum` ;
- `README.md` ;
- la documentation ;
- les fichiers de configuration ;
- les fichiers de build ;
- les workflows CI ;
- les scripts ;
- les templates ;
- les tests ;
- les dépendances ;
- l'historique Git utile à la compréhension des changements récents.

Utilise les commandes de diagnostic adaptées, par exemple :

```bash
pwd
git status --short --branch
git log -5 --oneline
git diff --stat
go version
go env
```

Inspecte les fichiers présents avant d'utiliser des commandes de build ou de nettoyage.

**Ne supprime et ne réinitialise jamais les modifications locales existantes.**

Si le dépôt contient des modifications non commitées, identifie-les et préserve-les.

Ne lance pas de `git reset --hard`, de `git clean -fd`, ni de commande équivalente susceptible de détruire le travail existant.

## 3. Phase 2 — Comprendre l'architecture réelle

Étudie les packages et les responsabilités de chacun.

Identifie notamment, s'ils existent :

- point d'entrée CLI ;
- commandes et sous-commandes ;
- configuration ;
- validation ;
- génération de projets ;
- templates intégrés ;
- templates externes ;
- registry de templates ;
- plan de génération ;
- métadonnées `.forge` ;
- opérations d'ajout et de suppression de fonctionnalités ;
- analyse des projets ;
- diagnostics ;
- vérification de cohérence ;
- inspection ;
- rollback ;
- sorties terminal ;
- sorties JSON ;
- gestion des erreurs ;
- système de version ;
- intégrations ;
- tests ;
- CI et distribution.

Pour chaque composant, détermine :

1. son emplacement ;
2. son rôle ;
3. ses dépendances internes ;
4. ses interfaces ;
5. les autres composants qui l'utilisent ;
6. ses tests ;
7. ses limites connues.

Produis une représentation textuelle de l'architecture actuelle.

Ne crée pas artificiellement des composants qui n'existent pas.

Si un composant attendu est absent, indique-le explicitement.

## 4. Phase 3 — Reconstituer les fonctionnalités

Examine chaque commande CLI réellement disponible.

Pour chacune, documente :

- sa syntaxe ;
- ses options ;
- son comportement ;
- les fichiers qu'elle lit ;
- les fichiers qu'elle écrit ;
- ses dépendances ;
- ses erreurs possibles ;
- ses tests existants.

Vérifie notamment, si ces commandes existent :

```text
forge init
forge add
forge remove
forge inspect
forge analyze
forge doctor
forge check
forge version
forge template list
forge template info
forge template install
forge template remove
forge template validate
forge template check
```

Cette liste est indicative.

La liste finale doit refléter les commandes réellement présentes dans le dépôt.

Pour chaque commande, vérifie si son comportement correspond à sa documentation.

Signale les écarts.

Ne prétends pas qu'une commande fonctionne avant de l'avoir vérifiée.

## 5. Phase 4 — Vérifier les versions précédentes

Détermine ce qui a réellement été implémenté dans les différentes versions.

Vérifie en particulier :

- la configuration personnalisable ;
- les architectures supportées ;
- les bases de données ;
- Docker ;
- l'authentification ;
- Swagger ou OpenAPI ;
- les tests générés ;
- la CI générée ;
- les différents langages ;
- les différents templates ;
- le registre des templates ;
- les templates externes ;
- l'autocomplétion ;
- les options non interactives ;
- les métadonnées `.forge` ;
- le rollback ;
- les sorties colorées et chronométrées.

Ne considère pas automatiquement que Go, TypeScript, JavaScript, Python, FastAPI, Django ou les templates externes sont complètement fonctionnels.

Vérifie ce qui existe réellement.

Pour chaque fonctionnalité, classe le résultat dans l'une de ces catégories :

- Implémentée et testée.
- Implémentée, mais insuffisamment testée.
- Partiellement implémentée.
- Présente, mais défectueuse.
- Documentée, mais absente du code.
- Absente.

## 6. Phase 5 — Établir un état initial des tests

Avant de corriger les bugs, exécute les vérifications pertinentes.

Pour un projet Go, commence notamment par :

```bash
go test ./...
go vet ./...
go build ./...
```

Adapte les commandes à la structure réelle du dépôt.

Si des outils de lint, de formatage ou de tests d'intégration sont configurés, examine-les également.

Vérifie aussi :

- les tests qui échouent ;
- les packages qui ne compilent pas ;
- les tests instables ;
- les dépendances indisponibles ;
- les problèmes de configuration ;
- les éventuels tests nécessitant Docker ou un service externe.

Distingue clairement :

1. les erreurs déjà présentes avant les corrections ;
2. les erreurs introduites par tes modifications ;
3. les problèmes d'environnement ;
4. les problèmes impossibles à vérifier dans l'environnement actuel.

Ne déclare pas une vérification réussie si elle n'a pas réellement été exécutée.

Si une commande ne peut pas être exécutée, indique pourquoi.

## 7. Phase 6 — Audit approfondi des bugs

Recherche les bugs dans le code et les comportements réels.

### A. Configuration

Vérifie :

- valeurs par défaut ;
- validation des entrées ;
- propagation des options ;
- cohérence entre configuration interactive et non interactive ;
- persistance de la configuration ;
- valeurs obsolètes ;
- configuration partiellement appliquée ;
- erreurs silencieuses.

### B. Génération des projets

Vérifie que les options choisies par l'utilisateur déterminent réellement les fichiers générés.

Exemples de régressions à rechercher :

- sélection de MySQL, mais génération de PostgreSQL ;
- désactivation de Docker, mais génération de fichiers Docker ;
- affichage de commandes Docker alors que Docker est désactivé ;
- dépendances inutiles ajoutées au projet ;
- variables d'environnement incompatibles avec la base de données sélectionnée ;
- fichiers propres à un langage générés dans un autre langage ;
- configuration affichée différente de la configuration réellement appliquée.

Ces exemples sont des pistes d'investigation, pas des bugs à déclarer sans preuve.

### C. Templates

Vérifie :

- fichiers manquants ;
- variables non remplacées ;
- chemins incorrects ;
- collisions entre fichiers ;
- capacités déclarées mais non implémentées ;
- templates invalides ;
- différences entre les templates intégrés et externes ;
- comportement lorsqu'un template est absent ou incompatible.

### D. Système de fichiers

Vérifie :

- chemins relatifs et absolus ;
- compatibilité Windows, Linux et macOS ;
- écrasements involontaires ;
- suppression de fichiers inattendus ;
- permissions ;
- symlinks ;
- traversée de chemins ;
- opérations partielles ;
- restauration après échec.

### E. Gestion des erreurs

Recherche :

- erreurs ignorées ;
- erreurs mal propagées ;
- messages trompeurs ;
- panics évitables ;
- erreurs remplacées par des valeurs par défaut ;
- états incohérents après échec.

### F. CLI

Vérifie :

- commandes et options ;
- arguments invalides ;
- valeurs par défaut ;
- codes de sortie ;
- sorties stdout/stderr ;
- mode silencieux ;
- mode JSON ;
- mode non interactif ;
- couleurs ;
- autocomplétion ;
- comportement dans un terminal non interactif.

### G. Sécurité

Vérifie notamment :

- validation des chemins ;
- gestion des secrets ;
- exécution de commandes externes ;
- utilisation de shell ;
- traitement des templates externes ;
- opérations destructives ;
- permissions des fichiers ;
- téléchargement de dépendances
