# Phase 12A — Dépôt APT officiel ForgeKit

## Contexte

ForgeKit est un CLI Go dont la version v0.3.0 est en cours de distribution.

La Phase 12 a déjà validé :

- `go test ./...` ✅
- `go vet ./...` ✅
- build Linux statique ✅
- packaging `.deb` ✅
- GoReleaser snapshot ✅
- injection de version par `ldflags` ✅
- génération d'un paquet Debian `forge` ✅
- GitHub Release déclenchée par les tags `v*`

Nous voulons maintenant ajouter une vraie distribution Linux via dépôt APT.

L'objectif utilisateur final est :

```bash
sudo apt update
sudo apt install forge
forge version
```

L'installation doit fonctionner sans que l'utilisateur ait besoin d'installer Go.

## Périmètre strict

Cette phase concerne UNIQUEMENT :

- dépôt APT ForgeKit ;
- signature GPG du dépôt ;
- publication via GitHub Pages ;
- génération automatique des métadonnées Debian ;
- intégration avec le workflow de release ;
- tests d'installation sur Ubuntu/Debian.

NE PAS implémenter dans cette phase :

- Windows ;
- macOS ;
- Homebrew ;
- WinGet ;
- installateur Windows ;
- nouvelle fonctionnalité métier ForgeKit ;
- modification de `forge add`, `remove`, `analyze`, `doctor`, etc. ;
- changement de schéma `.forge`.

# 3. Structure du dépôt APT

Créer une structure claire permettant de servir un dépôt Debian classique :

```text
apt/
├── pool/
│   └── main/
│       └── f/
│           └── forge/
│               └── forge_<version>_amd64.deb
│
├── dists/
│   └── stable/
│       ├── InRelease
│       ├── Release
│       └── main/
│           └── binary-amd64/
│               ├── Packages
│               └── Packages.gz
│
└── gpg/
    └── forgekit-archive-keyring.gpg
```

Ne pas inventer une structure propriétaire.

Utiliser une structure compatible avec `apt`.

---

# 4. Distribution

Le dépôt doit être présenté comme :

```text
distribution: stable
component: main
architecture: amd64
```

La ligne APT finale doit être :

```text
deb [signed-by=/usr/share/keyrings/forgekit.gpg] https://demetrius-ch.github.io/forgekit stable main
```

L'utilisateur devra pouvoir faire :

```bash
sudo apt update
sudo apt install forge
```

---

# 5. Signature GPG

Mettre en place une clé GPG dédiée au dépôt ForgeKit.

IMPORTANT :

Cette clé ne doit PAS être :

- la clé SSH GitHub ;
- une clé personnelle de développeur ;
- une clé privée commitée dans Git ;
- une clé utilisée directement pour les commits Git.

Elle est exclusivement destinée à signer le dépôt APT.

Nom recommandé :

```text
ForgeKit APT Repository
```

Email :

```text
packages@forgekit.dev
```

Si le domaine `forgekit.dev` n'existe pas réellement ou si cette adresse ne peut pas être utilisée, choisir une identité cohérente avec le projet sans prétendre qu'une adresse existe réellement.

La clé privée doit rester dans GitHub Secrets.

Ne jamais faire :

```text
git add private-key.gpg
```

Ne jamais mettre la clé privée dans :

```text
apt/
```

---

# 6. GitHub Secrets

Prévoir des secrets GitHub pour la publication.

Noms recommandés :

```text
FORGEKIT_APT_GPG_PRIVATE_KEY
FORGEKIT_APT_GPG_PASSPHRASE
```

Si le workflow peut fonctionner avec une clé protégée sans passphrase ou si une meilleure stratégie est nécessaire, expliquer clairement le choix avant de modifier le workflow.

Ne jamais afficher la valeur des secrets dans les logs.

Ne jamais faire :

```bash
echo "$FORGEKIT_APT_GPG_PRIVATE_KEY"
```

dans un workflow.

---

# 7. Clé publique

La clé publique doit être distribuable aux utilisateurs.

Prévoir :

```text
apt/gpg/forgekit-archive-keyring.gpg
```

ou une forme ASCII armor si nécessaire.

La procédure d'installation doit être claire.

Exemple :

```bash
curl -fsSL https://demetrius-ch.github.io/forgekit/gpg/forgekit.gpg \
  | sudo gpg --dearmor -o /usr/share/keyrings/forgekit.gpg
```

Puis :

```bash
echo "deb [signed-by=/usr/share/keyrings/forgekit.gpg] https://demetrius-ch.github.io/forgekit stable main" \
  | sudo tee /etc/apt/sources.list.d/forgekit.list
```

Puis :

```bash
sudo apt update
sudo apt install forge
```

Adapter cette procédure si le format final de la clé publique nécessite une autre méthode.

# 8. Génération Packages

Le dépôt doit générer correctement :

```text
Packages
Packages.gz
```

À partir du `.deb`.

Utiliser des outils Debian standards, par exemple :

```bash
dpkg-scanpackages
```

ou un outil équivalent fiable.

Ne pas générer manuellement le contenu de `Packages`.

Vérifier que le résultat contient notamment :

```text
Package: forge
Version: 0.3.0
Architecture: amd64
```

et que les champs nécessaires au téléchargement du paquet sont présents.

# 9. Génération Release

Créer :

```text
dists/stable/Release
```

avec les informations correctes :

```text
Origin: ForgeKit
Label: ForgeKit
Suite: stable
Codename: stable
Architectures: amd64
Components: main
```

Inclure les hashes nécessaires des fichiers Debian.

Ne pas écrire une fausse somme de contrôle.

Les hashes doivent être calculés à partir des fichiers réellement présents.

# 10. Signature du dépôt

Créer au minimum :

```text
InRelease
```

signé avec la clé GPG du dépôt.

Si nécessaire, générer également :

```text
Release.gpg
```

Le dépôt doit être vérifiable par APT.

Tester que :

```bash
sudo apt update
```

ne produit pas :

```text
NO_PUBKEY
```

ni :

```text
The repository is not signed
```

ni :

```text
InRelease is not valid
```

ni avertissement nécessitant :

```text
--allow-unauthenticated
```

Interdiction d'utiliser une solution qui contourne la vérification cryptographique.



Le workflow doit être idempotent autant que possible.

```text

```

# 14. Gestion des anciennes versions

Le dépôt doit pouvoir contenir plusieurs versions si nécessaire.

Par exemple :

```text
forge_0.3.0_amd64.deb
forge_0.3.1_amd64.deb
forge_0.4.0_amd64.deb
```

APT doit sélectionner la version la plus récente compatible.

Ne pas supprimer aveuglément toutes les anciennes versions.

Proposer une politique raisonnable de rétention.

---

# 15. Compatibilité avec GoReleaser

Le système APT doit réutiliser le `.deb` déjà produit par GoReleaser.

Ne pas recréer un deuxième système de packaging Debian inutilement.

Le pipeline doit idéalement faire :

```text
GoReleaser
    │
    └── forge_0.3.0_linux_amd64.deb
                │
                ▼
         dépôt APT
```

Le paquet doit rester le même.

Vérifier :

```bash
dpkg-deb -I forge_0.3.0_linux_amd64.deb
```

# 17. Test de sécurité

Tester explicitement le comportement lorsque :

- la clé publique n'est pas installée ;
- le dépôt est signé avec une mauvaise clé ;
- `InRelease` est modifié ;
- `Packages.gz` est modifié ;
- le `.deb` est modifié.

APT doit refuser les données falsifiées.

Ne jamais désactiver la vérification de signature pour faire passer le test.

# 28. Critères d'acceptation

La Phase 12A est considérée comme réussie uniquement si :

- [ ] Le dépôt APT possède une structure Debian valide.
- [ ] `Packages` est généré automatiquement.
- [ ] `Packages.gz` est généré automatiquement.
- [ ] `Release` est généré automatiquement.
- [ ] `InRelease` est signé.
- [ ] La clé privée n'est jamais présente dans Git.
- [ ] La clé privée n'est jamais publiée.
- [ ] La clé publique est distribuable.
- [ ] GitHub Pages sert correctement le dépôt.
- [ ] `apt update` fonctionne sans erreur de signature.
- [ ] `apt install forge` fonctionne.
- [ ] Aucun `--allow-unauthenticated` n'est nécessaire.
- [ ] `forge version` fonctionne après installation.
- [ ] Le paquet installé correspond au `.deb` produit par GoReleaser.
- [ ] Les anciennes versions sont correctement gérées.
- [ ] Le pipeline est reproductible.
- [ ] Le système fonctionne avec une nouvelle version sans modification manuelle de la configuration.
- [ ] Les tests ForgeKit existants restent verts.
- [ ] Aucun changement n'est apporté à Windows/macOS dans cette phase.
- [ ] Aucun nouveau tag n'est créé.

## Priorité

Ordre de priorité :

```text
1. Sécurité du dépôt
2. Intégrité cryptographique
3. Installation APT fonctionnelle
4. Automatisation GitHub Actions
5. Reproductibilité
6. Documentation
7. Confort développeur
```

Ne pas sacrifier la sécurité ou l'intégrité APT pour obtenir rapidement un `apt install`.

Commence par analyser le workflow actuel et le `.goreleaser.yaml`, puis implémente Phase 12A progressivement. Avant toute modification importante de l'architecture existante, explique le choix.
